## 3. 架构与结构

### 3.1 模块依赖

```
app ──✗──> anotherviewer-core   (无 Gradle 依赖！并行复制 client/ 包)
anotherviewer-web ──> anotherviewer-core  (implementation)
web-frontend ──> anotherviewer-web  (HTTP/WS 运行时；构建产物嵌入 JAR)
```

**关键问题**: `app` 和 `anotherviewer-core` 各自维护一份 `client/` 包（解析器、数据模型、SiteEngine），共 ~22 个解析器 + ~25 个数据模型文件的重复。`client/data/` 目录在两侧均 git-ignored，暗示有代码生成或符号链接机制，但仍是维护负担和漂移风险。

### 3.2 架构模式对比

| 层 | 模式 | 评价 |
|----|------|------|
| Android | 静态单例 + Scene 自定义导航 + AsyncTask + EventBus | 无 ViewModel/Lifecycle/DI，大量过时 API |
| Web 后端 | Controller → Service → Repository → Entity（标准 Spring 分层） | 清晰规范，DTO 与 Entity 分离 |
| Web 前端 | Vue 3 Composition API + Pinia + 功能/层级混合组织 | 现代化，TypeScript strict，组件契约文件 |

### 3.3 亮点

- **契约驱动**: `contracts/` 目录含 OpenAPI 3.0.3（3444 行）、JSON Schema 同步协议、WebSocket 协议、备份格式、可观测性规范、响应式策略 — 共 7 份契约文档
- **ADR**: 有架构决策记录（单用户模型、备份分片策略）
- **data-dir 约定**: 所有服务端状态从单一 `--data-dir` 派生，备份/迁移与路径无关
- **前端设计令牌**: 709 行 CSS 变量从 Android 资源忠实移植，3 主题 + WCAG AA 对比度回归测试

## 4. Web 后端

### 4.1 API 层（19 Controller，~60 端点）

**优点**: 一致的 `/api/v1/` 前缀，DTO 与 Entity 分离，`DownloadService.toItem()` 主动置空 `downloadDir` 防路径泄漏。

**问题**:
- 输入验证仅覆盖 `AuthDto` 和 `HistoryDto`，其余 `@RequestBody` 无 `@Valid`
- `GalleryController.search` 的 `pageSize` 无上限
- `FavoriteController.removeFavorite` 用 DELETE + RequestBody（兼容性风险）
- 部分端点返回无界全量列表（download list, sync pull, favorites, quick searches）

### 4.2 数据层

- SQLite + Hibernate community dialect，`open-in-view: false`（正确）
- **无迁移工具**（Critical）：`ddl-auto: update` 自动变更 schema
- N+1 / 全表扫描：`SyncService.pull` 对 7 种实体 `findAll().filter{}`；`DownloadService` 用 `findByState(3).size` 代替 `countByState()`
- `adoptNullOwnership` 每次 push/pull 都执行 7 次 `findAllByUsernameIsNull()` 扫描

### 4.3 服务层

- 25 个 Service，职责分离良好
- 错误处理三种范式共存：Boolean 返回、`AuthResponse` 结果对象、Kotlin `Result`
- 两种并发模型：DownloadService 用 ThreadPoolExecutor，ImageProcessingService 用 kotlinx.coroutines
- `DownloadService` 的取消逻辑设计精良（AtomicBoolean + CountDownLatch + 协作式检查）

### 4.4 同步系统

- 高水位增量同步设计正确，冲突解决策略（union merge / LWW / 5s skew tolerance）文档化且合理
- **但实现架空了设计**: pull 全表扫描 + 内存过滤，无 `findByUsernameAndLastModifiedGreaterThan` 派生查询
- Tombstone 永不回收（soft-delete 表单调增长）
- 7 种实体的字段映射全部手写（~25 字段/实体），添加字段需改多处，遗漏风险高

## 6. Android 客户端

### 6.1 同步引擎（最强模块）

`webui/WebUiSyncEngine.java`（900 行）是整个代码库中文档最完善、设计最谨慎的部分：
- 快照/待删集合差分逻辑正确，处理了复活场景
- 软删/硬删 tombstone 语义清晰且与 CONTEXT.md 领域模型一致
- 推送分块（500/批），失败不清除 pending 集合（幂等自愈）
- 凭证用 AndroidKeyStore AES/GCM 加密存储

**但**: 同步仅手动触发，无 WorkManager/AlarmManager 调度，无自动重试/退避。

### 6.2 架构债务

- 无 ViewModel / Lifecycle / Repository / DI — 全是静态单例 + AsyncTask
- 524 Java 文件 vs 50 Kotlin — 现代化程度极低
- greenDAO 3.0（已停止维护），迁移用 raw SQL try/catch
- OkHttp 3.14.9 故意固定（注释："还是旧版稳定好用"）
- fastjson 1.2.83（safe mode 缓解，但仍是供应链风险）

### 6.3 安全

- ✅ AndroidKeyStore 加密 token
- ✅ fastjson safe mode
- ✅ 独立隔离的 OkHttp 客户端用于 LAN 同步
- ⚠️ 全局明文流量许可 + 信任用户 CA
- ⚠️ 3 个 exported Activity 无权限保护
- ⚠️ WebView JS 无域名白名单
- ⚠️ CAMERA 权限理由可疑（"用于获取 wifi 状态"）

## 7. 同步协议与数据模型一致性

### 7.1 协议评估

同步协议在三层（契约 schema、服务端实现、Android 实现）之间高度一致：
- 7 种实体的合并策略、skew tolerance、tombstone 语义完全匹配
- Mock server 忠实复制了合并逻辑
- Android 删除检测（快照/待删差分）健壮

### 7.2 已发现的不一致（按影响排序）

| # | 不一致 | 影响 |
|---|--------|------|
| 1 | History `mode` 字段：Android 有、服务端 Entity 无此列 | 跨设备同步丢失搜索模式上下文 |
| 2 | Download `label`：Android/wire 为 String（标签名），服务端 Entity 为 Int（标签 ID） | 字段未映射，依赖独立的 downloadLabels 实体 |
| 3 | Android `EntityCounts` 缺 `downloadLabels` 字段 | 状态显示少计一类实体 |
| 4 | `fileSize` 在 schema 中定义但服务端 DTO 不含 | 契约/实现分歧；mock 发送但真实服务端不发 |
| 5 | Mock server 缺 `since===0` 全量拉取保护 | 首次对 mock 同步可能遗漏 legacy 记录 |
| 6 | Bookmark `page` 存为服务端 `note` 字符串列 | 功能正确但语义不清 |
| 7 | Download `archiveUri` 在 wire schema 中但为设备本地字段 | 可能误导实现者 |

## 8. 安全

### 8.1 做得好的

- BCrypt 密码哈希（10 轮）
- Token SHA-256 哈希存储（原始 token 不落盘）
- 配对码 SecureRandom 生成（32 字符表 × 6 位 ≈ 90 bit 熵），10 分钟 TTL + 一次性
- 备份恢复路径遍历防护（zip + 7z 双重校验）
- SSRF 主机白名单（archive/torrent）
- CSRF 禁用合理（无状态 Bearer token API）
- systemd 部署加固（专用用户、NoNewPrivileges、ProtectSystem=strict）
- Android 凭证 AndroidKeyStore AES/GCM 加密

### 8.2 需要修复的

见 [§2 发现汇总](#2-发现汇总按严重度) 中 C-1, H-1, H-2, M-1 ~ M-4, M-8 ~ M-12。

## 11. 优先修复建议

### 第一梯队（安全/数据完整性）

1. **移除 CI 硬编码密码** → 改用 Azure DevOps secret variables / secure file（C-1）
2. **引入 Flyway/Liquibase** → 从当前 schema 生成 baseline，所有后续变更走迁移（C-2）
3. **升级 OkHttp** → 至少 4.12+（修复已知 CVE）；Android 端评估升级路径（H-2）
4. **同步 pull 加索引查询** → `findByUsernameAndLastModifiedGreaterThan` 替代 `findAll().filter{}`（H-3）
5. **登录速率限制** → 简单的内存计数器 + 指数退避即可（M-2）

### 第二梯队（架构/可维护性）

6. **统一错误响应格式** → 定义 `ApiError` envelope + 全局 `@RestControllerAdvice`（M-6）
7. **补全输入验证** → 所有 `@RequestBody` 加 `@Valid` + DTO 约束注解（M-5）
8. **DownloadService 并发保护** → `@Version` 乐观锁或 `@Transactional`（M-7）
9. **修复数据模型不一致** → History `mode` 列、Download `label` 类型对齐（M-13, M-14）
10. **Android targetSdk 升级到 34+** → 处理 scoped storage、包可见性等适配（H-4）

### 第三梯队（质量/技术债）

11. **Android 同步引擎测试** → 至少覆盖 push/pull/tombstone/ resurrection 路径
12. **前端 reader 组件测试** → 6 个未测试组件 + WebSocket composable
13. **Docker 非 root 用户** → `USER 1000` + 文件权限调整（M-12）
14. **CORS 收紧** → 默认改为前端 origin，`*` 仅作开发覆盖（M-3）
15. **app ↔ core 代码去重** → 让 app 依赖 core，消除并行复制的 client/ 包
