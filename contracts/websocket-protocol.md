> **Status**: Frozen (Wave 0 contract)

> **Created**: 2026-07-28
> **Owner**: CA5
> **Depends on**: `WebSocketConfig.kt` (STOMP/SockJS), roadmap §1.3, §3.4, §3.5

## 1. Overview & Connection Lifecycle

### 1.1 Transport

The protocol uses **STOMP 1.2** over **SockJS** as the transport layer, matching the
existing `WebSocketConfig.kt` implementation (`@EnableWebSocketMessageBroker`).

| Property | Value |
|----------|-------|
| Endpoint | `ws://{host}:{port}/ws` (native WebSocket) |
| SockJS fallback | `http://{host}:{port}/ws` (auto-negotiated by SockJS client) |
| Broker prefix | `/topic` (server → client broadcasts) |
| Application prefix | `/app` (client → server commands) |
| Default port | `8080` (configurable via `server.port`) |

### 1.2 Connection Lifecycle

```
Client                                          Server
  │                                               │
  │──── SockJS handshake (/ws/info) ────────────▶│
  │◀─── transport negotiation ──────────────────│
  │                                               │
  │──── STOMP CONNECT ──────────────────────────▶│
  │     headers:                                  │
  │       login: {token}                          │
  │       passcode: ""                            │
  │       heart-beat: 10000,10000                 │
  │       accept-version: 1.2                     │
  │◀─── STOMP CONNECTED ────────────────────────│
  │     headers:                                  │
  │       version: 1.2                            │
  │       heart-beat: 10000,10000                 │
  │                                               │
  │──── SUBSCRIBE /topic/download/all ──────────▶│
  │──── SUBSCRIBE /topic/process/{taskId} ──────▶│
  │──── SUBSCRIBE /topic/gallery/{galleryId} ───▶│
  │◀─── messages flow ──────────────────────────│
  │                                               │
  │──── heart-beat (newline) ───────────────────▶│
  │◀─── heart-beat (newline) ───────────────────│
  │                                               │
  │──── DISCONNECT ─────────────────────────────▶│
  │◀─── DISCONNECT receipt ─────────────────────│
  │                                               │
```

### 1.3 Authentication

Authentication is performed via the STOMP `CONNECT` frame:

```
login: {api-token}
passcode: ""
```

The `api-token` is the same token generated by the server for Android sync
(see roadmap §2.1). For browser/PWA clients on the same LAN, the server MAY
accept connections without a token when `ehviewer.web.auth-required=false`
(default for development).

**Alternative (query parameter)**: For clients that cannot set STOMP headers
(e.g., raw WebSocket without STOMP), the token can be passed as:
```
ws://{host}:{port}/ws/websocket?token={api-token}
```

### 1.4 Heartbeat

STOMP heart-beat is used for connection liveness detection:

| Direction | Interval | Notes |
|-----------|----------|-------|
| Client → Server | 10,000 ms | Client sends newline (`\n`) if no other traffic |
| Server → Client | 10,000 ms | Server sends newline if no other traffic |

If no data (including heart-beats) is received for **3× the negotiated interval**
(30 seconds), the connection is considered dead.

### 1.5 Reconnection Strategy

Clients MUST implement exponential backoff reconnection:

```typescript
const RECONNECT_CONFIG = {
  initialDelayMs: 1000,
  maxDelayMs: 30000,
  multiplier: 2,
  jitter: 0.3,           // ±30% randomization
  maxAttempts: Infinity,  // never give up while app is visible
}
```

**Behavior**:
1. On disconnect, wait `initialDelayMs` (± jitter) before first reconnect.
2. Each failed attempt multiplies delay by `multiplier`, capped at `maxDelayMs`.
3. On successful reconnect, reset delay to `initialDelayMs`.
4. After reconnect, client MUST re-subscribe to all previously active topics.
5. Client SHOULD request a state snapshot via REST after reconnect to catch
   missed events (e.g., `GET /api/download/list`, `GET /api/process/status`).
6. When the browser tab is hidden (`document.visibilityState === 'hidden'`),
   pause reconnection attempts; resume on visibility change.

**SockJS built-in reconnect**: The `@stomp/stompjs` client supports
`reconnectDelay` natively. Configure:

```typescript
const client = new Client({
  webSocketFactory: () => new SockJS('/ws'),
  reconnectDelay: 5000,       // base delay
  heartbeatIncoming: 10000,
  heartbeatOutgoing: 10000,
})
```

For exponential backoff, implement a custom `onStompError` / `onWebSocketClose`
handler that adjusts `client.reconnectDelay` before each attempt.

## 2. Message Envelope Format

All server → client messages on `/topic/*` destinations use a unified JSON envelope:

```typescript
interface WsEnvelope<T = unknown> {
  /** Message type identifier (dot-separated namespace) */
  type: string
  /** Epoch milliseconds when the event occurred on the server */
  timestamp: number
  /** Protocol version (semver major.minor) for forward compatibility */
  version: string
  /** Message payload — shape determined by `type` */
  payload: T
}
```

**Example**:

```json
{
  "type": "download.progress",
  "timestamp": 1722182400000,
  "version": "1.0",
  "payload": {
    "taskId": "dl-1234567890",
    "galleryId": 1887292,
    "galleryName": "[Artist] Gallery Title",
    "downloadedPages": 15,
    "totalPages": 42,
    "speed": 2097152,
    "state": "downloading"
  }
}
```

### 2.1 Backward Compatibility

The existing `DownloadProgress` DTO (`gid`, `state`, `downloaded`, `total`,
`speed`, `label`) is superseded by the envelope format above. During migration:

- Server SHALL send both the legacy bare DTO and the new envelope on separate
  topics (`/topic/download/{gid}` legacy, `/topic/download/progress` new).
- Frontend SHOULD migrate to the envelope-based topics.
- Legacy topics are deprecated and will be removed in protocol v2.0.

### 2.2 Type Namespace Convention

Message types follow `{domain}.{event}` naming:

| Domain | Scope |
|--------|-------|
| `download` | Download task lifecycle |
| `process` | Image processing pipeline |
| `image` | Individual image events |
| `sync` | Device synchronization |
| `system` | Server health and errors |

## 3. Server → Client Message Types

### 3.1 Download Progress

#### `download.progress`

Emitted periodically (throttled to max 2 events/second per task) while a
download is active.

**Topic**: `/topic/download/progress` (all tasks) or `/topic/download/{galleryId}` (single gallery)

```typescript
interface DownloadProgressPayload {
  /** Unique download task identifier (server-assigned) */
  taskId: string
  /** E-Hentai gallery ID (gid) */
  galleryId: number
  /** Gallery display title */
  galleryName: string
  /** Number of pages downloaded so far */
  downloadedPages: number
  /** Total pages in the gallery */
  totalPages: number
  /** Current download speed in bytes/second (0 if paused) */
  speed: number
  /** Current task state */
  state: 'downloading' | 'paused' | 'completed' | 'failed'
  /** Error message (present only when state === 'failed') */
  error?: string
  /** Download label/category ID */
  label?: number
}
```

#### `download.state`

Emitted once on each state transition (start, pause, resume, complete, fail).

**Topic**: `/topic/download/state` (all) or `/topic/download/{galleryId}` (single)

```typescript
interface DownloadStatePayload {
  /** Unique download task identifier */
  taskId: string
  /** E-Hentai gallery ID */
  galleryId: number
  /** New state after transition */
  state: 'pending' | 'downloading' | 'paused' | 'completed' | 'failed'
  /** Previous state before transition */
  previousState: 'pending' | 'downloading' | 'paused' | 'completed' | 'failed'
  /** Error message (present only when state === 'failed') */
  error?: string
}
```

#### `download.batch`

Emitted when a batch operation completes (affects multiple tasks).

**Topic**: `/topic/download/batch`

```typescript
interface DownloadBatchPayload {
  /** Batch operation type */
  operation: 'startAll' | 'pauseAll' | 'deleteAll' | 'deleteCompleted'
  /** Task IDs affected by the operation */
  affectedIds: string[]
  /** Number of tasks that failed to apply the operation (e.g., already deleted) */
  failedCount: number
}
```

### 3.2 Image Processing

#### `process.started`

Emitted when an image enhancement job begins processing.

**Topic**: `/topic/process/{taskId}` or `/topic/process/all`

```typescript
interface ProcessStartedPayload {
  /** Processing task identifier */
  taskId: string
  /** Gallery being processed */
  galleryId: number
  /** Total pages to process */
  totalPages: number
  /** Processing type being applied */
  processingType: 'UPSCALE_2X' | 'UPSCALE_4X' | 'DENOISE' | 'DENOISE_UPSCALE'
  /** Processor identifier (e.g., "waifu2x", "noop") */
  processorId: string
}
```

#### `process.progress`

Emitted after each page is processed (throttled to max 5 events/second).

**Topic**: `/topic/process/{taskId}` or `/topic/process/all`

```typescript
interface ProcessProgressPayload {
  /** Processing task identifier */
  taskId: string
  /** Gallery being processed */
  galleryId: number
  /** Number of pages processed so far */
  processedPages: number
  /** Total pages in the job */
  totalPages: number
  /** The page number just completed (1-based) */
  currentPage: number
}
```

#### `process.completed`

Emitted when all pages in a processing job finish successfully.

**Topic**: `/topic/process/{taskId}` or `/topic/process/all`

```typescript
interface ProcessCompletedPayload {
  /** Processing task identifier */
  taskId: string
  /** Gallery that was processed */
  galleryId: number
  /** Number of pages successfully enhanced */
  enhancedPages: number
  /** Total elapsed time in milliseconds */
  elapsedMs: number
}
```

#### `process.failed`

Emitted when a processing job fails (unrecoverable error).

**Topic**: `/topic/process/{taskId}` or `/topic/process/all`

```typescript
interface ProcessFailedPayload {
  /** Processing task identifier */
  taskId: string
  /** Gallery that was being processed */
  galleryId: number
  /** Human-readable error description */
  error: string
  /** The page number that caused the failure (1-based), if applicable */
  failedPage?: number
  /** Number of pages successfully processed before failure */
  processedBeforeFailure: number
}
```

### 3.3 AI Enhancement (Reader Hot-Swap)

#### `image.enhanced.ready`

**Critical message for I3 (AI enhancement hot-swap).**

Emitted when a single page's enhanced version becomes available. The reader
component listens for this message and hot-swaps the image `src` without
interrupting the reading experience.

**Topic**: `/topic/gallery/{galleryId}/enhanced`

```typescript
interface ImageEnhancedReadyPayload {
  /** Gallery containing the enhanced page */
  galleryId: number
  /** Page number (1-based) */
  page: number
  /** URL to fetch the enhanced image (relative or absolute) */
  enhancedUrl: string
  /** URL of the original image (for reference/fallback) */
  originalUrl: string
  /** Processing type that was applied */
  processingType: 'UPSCALE_2X' | 'UPSCALE_4X' | 'DENOISE' | 'DENOISE_UPSCALE'
  /** Enhanced image dimensions (pixels) */
  width: number
  height: number
  /** File size in bytes (for cache management) */
  fileSize: number
}
```

**Client behavior on receipt** (normative for I3 implementation):

1. Check if the page is currently displayed or in the preload cache.
2. Create a new `Image()` object, set `src = enhancedUrl`.
3. On `load` event, swap the displayed/cached image reference atomically.
4. Do NOT trigger a re-layout or scroll position change.
5. If the enhanced image fails to load, silently keep the original.
6. Update any local cache metadata to prefer the enhanced URL for future loads.

**Emission pattern**: The server emits one `image.enhanced.ready` per page as
each completes (not batched). This allows the reader to progressively upgrade
pages as the user reads, rather than waiting for the entire gallery.

**Topic**: `/topic/sync`


### 3.5 System

#### `system.health`

Emitted periodically (default: every 30 seconds) with server health metrics.

**Topic**: `/topic/system/health`

```typescript
interface SystemHealthPayload {
  /** Disk cache usage in bytes */
  cacheUsage: number
  /** Disk cache capacity in bytes */
  cacheCapacity: number
  /** Number of currently active download tasks */
  activeDownloads: number
  /** Number of tasks in the processing queue (pending + processing) */
  processingQueue: number
  /** JVM heap memory usage in bytes */
  memoryUsage: number
  /** JVM max heap in bytes */
  memoryMax: number
  /** Server uptime in seconds */
  uptimeSeconds: number
  /** Whether the image processor (waifu2x) is reachable */
  processorAvailable: boolean
}
```

#### `system.error`

Emitted on significant server errors that clients should surface to the user.

**Topic**: `/topic/system/error`

```typescript
interface SystemErrorPayload {
  /** Machine-readable error code */
  code: string
  /** Human-readable error message */
  message: string
  /** Additional context (stack trace excerpt, affected resource, etc.) */
  details?: string
  /** Severity level */
  severity: 'warning' | 'error' | 'critical'
}
```

**Defined error codes**:

| Code | Meaning |
|------|---------|
| `AUTH_COOKIE_EXPIRED` | E-Hentai login session expired; re-login required |
| `RATE_LIMITED_509` | E-Hentai 509 bandwidth limit hit; downloads paused |
| `PROCESSOR_UNAVAILABLE` | waifu2x service unreachable |
| `DISK_FULL` | Insufficient disk space for downloads/cache |
| `SYNC_FAILED` | Sync with a remote device failed |

## 4. Client → Server Messages

Client messages are sent to `/app/*` destinations (STOMP SEND frames).

### 4.1 `subscribe`

Subscribe to filtered event streams beyond the default topic subscriptions.

**Destination**: `/app/subscribe`

```typescript
interface SubscribeRequest {
  /** Message types to subscribe to (e.g., ["download.progress", "process.progress"]) */
  types?: string[]
  /** Gallery IDs to filter events for (empty = all galleries) */
  galleryIds?: number[]
  /** Whether to receive image.enhanced.ready for the specified galleries */
  enhancedReady?: boolean
}
```

**Behavior**:
- The server registers the client's interest and starts sending matching events.
- If `galleryIds` is provided, the client will ONLY receive events for those
  galleries on the filtered topics.
- `enhancedReady: true` subscribes the client to `/topic/gallery/{id}/enhanced`
  for each specified gallery ID.

**Response**: The server sends a confirmation on `/topic/subscription/confirm`:

```typescript
interface SubscriptionConfirm {
  /** Subscribed message types */
  types: string[]
  /** Subscribed gallery IDs */
  galleryIds: number[]
  /** Subscription session ID (for unsubscribe) */
  subscriptionId: string
}
```

### 4.2 `unsubscribe`

Remove previously registered subscriptions.

**Destination**: `/app/unsubscribe`

```typescript
interface UnsubscribeRequest {
  /** Subscription ID returned from subscribe confirmation */
  subscriptionId?: string
  /** Or specify types/galleryIds to unsubscribe selectively */
  types?: string[]
  galleryIds?: number[]
}
```

### 4.3 `ping`

Client-initiated heartbeat (application-level, in addition to STOMP heart-beat).
Useful for measuring round-trip latency.

**Destination**: `/app/ping`

```typescript
interface PingRequest {
  /** Client timestamp (epoch millis) for RTT calculation */
  clientTime: number
}
```

**Response** on `/topic/pong`:

```typescript
interface PongResponse {
  /** Echoed client timestamp */
  clientTime: number
  /** Server timestamp (epoch millis) */
  serverTime: number
}
```

## 5. Error Handling & Reconnection

### 5.1 STOMP Error Frames

If the server sends a STOMP ERROR frame, the client receives it via the
`onStompError` callback. The ERROR frame body contains:

```
message: {short description}
content-type: application/json

{"code": "...", "message": "...", "details": "..."}
```

**Client behavior on STOMP ERROR**:
1. Log the error.
2. If the error is recoverable (e.g., subscription limit), adjust and reconnect.
3. If the error is fatal (e.g., protocol version mismatch), show user-facing error.

### 5.2 Connection Loss Detection

| Signal | Detection Method | Action |
|--------|-----------------|--------|
| Clean disconnect | STOMP DISCONNECT receipt | No reconnect needed |
| Network loss | Heart-beat timeout (30s) | Begin reconnection |
| Server crash | SockJS transport error | Begin reconnection |
| Tab hidden | `visibilitychange` event | Pause reconnect, resume on visible |

### 5.3 Missed Message Recovery

WebSocket is not guaranteed delivery. After reconnection:

1. Client calls `GET /api/download/list` to get current download states.
2. Client calls `GET /api/process/status` to get active processing jobs.
3. Client re-subscribes to all active topics.
4. For `image.enhanced.ready` events missed during disconnection, the reader
   SHOULD request enhanced image availability via
   `GET /api/image/{galleryId}/{page}?enhanced=true` when displaying a page.

### 5.4 Server-Side Error Propagation

When a server error occurs that affects connected clients:

1. Emit `system.error` on `/topic/system/error`.
2. If the error affects a specific download, also emit `download.state` with
   `state: 'failed'` and the error message.
3. If the error affects a processing job, also emit `process.failed`.

## 6. Subscription Model

### 6.1 Topic Hierarchy

```
/topic/
├── download/
│   ├── progress          ← all download progress events
│   ├── state             ← all download state changes
│   ├── batch             ← batch operation results
│   └── {galleryId}       ← progress + state for a specific gallery
├── process/
│   ├── all               ← all processing events
│   └── {taskId}          ← events for a specific processing job
├── gallery/
│   └── {galleryId}/
│       └── enhanced      ← image.enhanced.ready for this gallery
├── sync                  ← sync.update + sync.conflict
├── system/
│   ├── health            ← periodic health metrics
│   └── error             ← server errors
├── pong                  ← ping responses
└── subscription/
    └── confirm           ← subscription confirmations
```

### 6.2 Default Subscriptions (on connect)

Clients SHOULD subscribe to these topics immediately after connection:

| Topic | Purpose |
|-------|---------|
| `/topic/download/progress` | Download list progress bars |
| `/topic/download/state` | Download state transitions |
| `/topic/download/batch` | Batch operation feedback |
| `/topic/system/error` | Critical error notifications |

### 6.3 On-Demand Subscriptions

These are subscribed when the user navigates to the relevant screen:

| Screen | Topics to Subscribe |
|--------|-------------------|
| Reader (gallery view) | `/topic/gallery/{galleryId}/enhanced` |
| Processing status | `/topic/process/{taskId}` or `/topic/process/all` |
| Settings (sync tab) | `/topic/sync` |
| Dashboard/status bar | `/topic/system/health` |

### 6.4 Gallery-Specific Filtering

For high-traffic servers with many concurrent downloads, clients can reduce
message volume by subscribing to gallery-specific topics:

- `/topic/download/{galleryId}` receives ONLY `download.progress` and
  `download.state` messages for that gallery.
- `/topic/gallery/{galleryId}/enhanced` receives ONLY `image.enhanced.ready`
  for that gallery.

The server publishes to both the "all" topic and the gallery-specific topic
for each event. Clients choose granularity based on their current view.

### 6.5 Message Throttling

To prevent overwhelming clients:

| Message Type | Max Rate | Strategy |
|-------------|----------|----------|
| `download.progress` | 2/sec per task | Server-side throttle; final state always sent |
| `process.progress` | 5/sec per task | Server-side throttle; page boundaries always sent |
| `system.health` | 1/30sec | Fixed interval |
| `image.enhanced.ready` | No throttle | One per page completion (naturally bounded by GPU) |

## 7. Versioning Strategy

### 7.1 Protocol Version

The protocol follows **semantic versioning** (MAJOR.MINOR.PATCH):

- **MAJOR**: Breaking changes (message removal, envelope restructure).
  Requires coordinated client + server upgrade.
- **MINOR**: Additive changes (new message types, new optional payload fields).
  Backward compatible; old clients ignore unknown types.
- **PATCH**: Documentation fixes, no wire changes.

Current version: **1.0.0**

### 7.2 Version Negotiation

1. The `version` field in every envelope carries the protocol version.
2. Clients SHOULD ignore messages with a MAJOR version higher than supported.
3. Clients SHOULD handle unknown `type` values gracefully (log + discard).
4. New optional fields in payloads MUST NOT break clients that don't read them.

### 7.3 Deprecation Policy

- Deprecated message types/topics are announced one MINOR version ahead.
- The `version` field in deprecated messages remains unchanged.
- Server logs a warning when a client subscribes to a deprecated topic.
- Deprecated topics are removed in the next MAJOR version.

### 7.4 Migration from Legacy Format

The existing bare `DownloadProgress` DTO (without envelope) on
`/topic/download/{gid}` is **deprecated as of v1.0.0**.

| Legacy | New (v1.0.0) |
|--------|-------------|
| `/topic/download/{gid}` (bare DTO) | `/topic/download/{galleryId}` (envelope) |
| `/topic/download/all` (bare DTO) | `/topic/download/progress` (envelope) |
| `gid` field | `galleryId` field |
| `state` as integer | `state` as string enum |
| `downloaded` | `downloadedPages` |
| `total` | `totalPages` |

Server SHALL publish on both legacy and new topics for one release cycle.
Frontend migration target: Wave 3 I2 (WS integration task).

```typescript
  'image.enhanced.ready': ImageEnhancedReadyPayload
  'sync.update': SyncUpdatePayload
  'sync.conflict': SyncConflictPayload
  'system.health': SystemHealthPayload
  'system.error': SystemErrorPayload
}

export type WsMessageType = keyof WsMessageMap

/** Type-safe envelope for a known message type */
export type TypedWsEnvelope<T extends WsMessageType> = WsEnvelope<WsMessageMap[T]>
```

### C.2 Message Publishing Pattern

```kotlin
// Server publishes to both "all" and specific topics:
fun publishDownloadProgress(progress: DownloadProgressPayload) {
    val envelope = WsEnvelope(
        type = "download.progress",
        timestamp = System.currentTimeMillis(),
        version = "1.0",
        payload = progress
    )
    // Broadcast to all subscribers
    messagingTemplate.convertAndSend("/topic/download/progress", envelope)
    // Gallery-specific topic
    messagingTemplate.convertAndSend("/topic/download/${progress.galleryId}", envelope)
}
```

## Appendix D: Client Integration Example (Vue 3)

```typescript
// web-frontend/src/composables/useEnhancedImage.ts (I3 task)
import { Client } from '@stomp/stompjs'
import SockJS from 'sockjs-client/dist/sockjs'
import type { WsEnvelope, ImageEnhancedReadyPayload } from '@/types/websocket'

export function useEnhancedImage(galleryId: number) {
  let client: Client | null = null
  const enhancedUrls = new Map<number, string>() // page → enhancedUrl

  function connect(onReady: (page: number, enhancedUrl: string) => void) {
    client = new Client({
      webSocketFactory: () => new SockJS('/ws'),
      reconnectDelay: 5000,
      heartbeatIncoming: 10000,
      heartbeatOutgoing: 10000,
      onConnect: () => {
        client?.subscribe(
          `/topic/gallery/${galleryId}/enhanced`,
          (message) => {
            const envelope = JSON.parse(message.body) as WsEnvelope<ImageEnhancedReadyPayload>
            if (envelope.type === 'image.enhanced.ready') {
              const { page, enhancedUrl } = envelope.payload
              enhancedUrls.set(page, enhancedUrl)
              onReady(page, enhancedUrl)
            }
          }
        )
      },
    })
    client.activate()
  }

  function disconnect() {
    client?.deactivate()
  }

  function getEnhancedUrl(page: number): string | undefined {
    return enhancedUrls.get(page)
  }

  return { connect, disconnect, getEnhancedUrl }
}
```
