## 1. Overview & Connection Lifecycle

### 1.1 Transport

The protocol uses **STOMP 1.2** over **SockJS** as the transport layer, matching the
existing `WebSocketConfig.kt` implementation (`@EnableWebSocketMessageBroker`).

| Property | Value |
|----------|-------|
| Endpoint | `ws://{host}:{port}/ws` (native WebSocket) |
| SockJS fallback | `http://{host}:{port}/ws` (auto-negotiated by SockJS client) |
| Broker prefix | `/topic` (server → client broadcasts) |
| Application prefix | `/app` (client → server commands) |
| Default port | `8080` (configurable via `server.port`) |
| Allowed origins | `EHVIEWER_WS_ORIGINS` env var, comma-separated; default `*`. Passed to `setAllowedOriginPatterns` (`WebSocketConfig.kt:28-32`) |

### 1.2 Connection Lifecycle

```
Client                                          Server
  │                                               │
  │──── SockJS handshake (/ws/info) ────────────▶│
  │◀─── transport negotiation ──────────────────│
  │                                               │
  │──── STOMP CONNECT ──────────────────────────▶│
  │     headers:                                  │
  │       login: {token}                          │
  │       passcode: ""                            │
  │       heart-beat: 10000,10000                 │
  │       accept-version: 1.2                     │
  │◀─── STOMP CONNECTED ────────────────────────│
  │     headers:                                  │
  │       version: 1.2                            │
  │       heart-beat: 10000,10000                 │
  │                                               │
  │──── SUBSCRIBE /topic/download/all ──────────▶│  (bare DTO, legacy)
  │──── SUBSCRIBE /topic/process/all ───────────▶│  (envelope)
  │──── SUBSCRIBE /topic/gallery/{gid}/enhanced ▶│  (envelope)
  │◀─── messages flow ──────────────────────────│
  │                                               │
  │──── heart-beat (newline) ───────────────────▶│
  │◀─── heart-beat (newline) ───────────────────│
  │                                               │
  │──── DISCONNECT ─────────────────────────────▶│
  │◀─── DISCONNECT receipt ─────────────────────│
  │                                               │
```

### 1.3 Authentication **[IMPLEMENTED]**

Authentication is performed via the STOMP `CONNECT` frame, validated by
`WsAuthChannelInterceptor` (`WsAuthChannelInterceptor.kt:26-46`):

```
login: {api-token}
passcode: ""
```

- The server reads the token from the `login` header; if absent, it falls back to
  an `Authorization: Bearer {token}` header (the frontend sends both, see
  `useWebSocket.ts` `buildConnectHeaders`). The `api-token` is the same token
  generated by the server for Android sync.
- The token is validated with `EhAuthService.validateToken`.
- **Enforcement is conditional**: the CONNECT is only inspected when
  `security.require_auth` is true — the `security.require_auth` DB config key
  (env override `EHVIEWER_REQUIRE_AUTH`). Default is **false** (LAN personal
  deployment, see `ServerConfigService.kt` defaults); with `require_auth=false`
  every CONNECT is accepted without token inspection.
- On rejection (missing/invalid token and `require_auth=true`) the server sends a
  STOMP **ERROR frame** with header `message: Authentication required` and an
  empty body, and rejects the CONNECT (no CONNECTED frame follows).

**Client behavior** (`useWebSocket.ts`): the frontend reads the token from
`localStorage` and includes `login` + `Authorization: Bearer …` in every CONNECT.
A STOMP ERROR before the first CONNECTED frame is treated as an auth failure: the
manager gives up immediately instead of retrying with the same headers, and
surfaces the server's `message` via `authError`.

> **Not implemented (aspirational)**: the query-parameter form
> `ws://{host}:{port}/ws/websocket?token={api-token}` is NOT supported by the
> server. Only STOMP CONNECT headers are accepted.

### 1.4 Heartbeat

STOMP heart-beat is used for connection liveness detection:

| Direction | Interval | Notes |
|-----------|----------|-------|
| Client → Server | 10,000 ms | Frontend sends `heartbeatOutgoing: 10000` |
| Server → Client | 10,000 ms | Frontend sends `heartbeatIncoming: 10000`; Spring broker default |

If no data (including heart-beats) is received for **3× the negotiated interval**
(30 seconds), the connection is considered dead.

### 1.5 Reconnection Strategy **[IMPLEMENTED]**

The frontend (`web-frontend/src/composables/useWebSocket.ts`) implements a
single app-wide STOMP-over-SockJS client with reference counting. Its reconnection
behavior:

```typescript
// useWebSocket.ts — actual client configuration
new Client({
  webSocketFactory: () => new SockJS('/ws'),
  reconnectDelay: 1000,             // initial delay (INITIAL_RECONNECT_DELAY_MS)
  maxReconnectDelay: 30000,         // backoff cap (MAX_RECONNECT_DELAY_MS)
  reconnectTimeMode: ReconnectionTimeMode.EXPONENTIAL,  // 1s → 2s → 4s → … → 30s
  heartbeatIncoming: 10000,
  heartbeatOutgoing: 10000,
  connectHeaders: { login: token, Authorization: `Bearer ${token}`, passcode: '' },
})
```

**Behavior**:
1. Exponential backoff starts at 1s and doubles per failed attempt, capped at 30s
   (`maxReconnectDelay`); the library resets to 1s on every successful connect.
2. **Give-up**: after `MAX_CONSECUTIVE_CONNECT_FAILURES = 3` consecutive failed
   connect attempts (no CONNECTED frame received), the manager stops the loop,
   sets `connectionState = 'error'`, and records the reason in `lastError` /
   `authError`. A subsequent explicit `connect()` re-arms the loop.
3. A STOMP ERROR on the CONNECT itself (e.g. `Authentication required`) gives up
   **immediately** — retrying identical headers cannot help (see §1.3).
4. On successful (re)connect, all registered subscriptions are re-established
   automatically via the subscription registry (`resubscribeAll`).
5. After reconnect, clients SHOULD fetch a state snapshot via REST to catch
   missed events: `GET /api/v1/download/list`, `GET /api/v1/process/status/{taskId}`.
6. **Visibility pause**: while the tab is hidden (`document.visibilityState ===
   'hidden'`) the socket is deactivated and reconnection paused; on
   `visibilitychange` back to visible, the connection resumes.
7. Stale-socket guards: activation is idempotent; CONNECTED frames from a
   superseded session are ignored — at most one active socket at a time.

> There is no "retry forever while visible" mode; the 3-failure give-up is the
> actual behavior.

## 2. Message Envelope Format

Server → client messages use **two wire formats** depending on the domain:

- **Envelope** `{type, timestamp, version, payload}` — used on processing topics
  (§3.2) and the enhanced-image topic (§3.3). Published by `ProcessingEventHandler`.
- **Bare DTO** — used on download topics (§3.1). The raw `DownloadProgress` DTO is
  sent directly, **no envelope**, by `DownloadProgressHandler`.

The envelope shape **[IMPLEMENTED]** (processing/enhanced topics):

```typescript
interface WsEnvelope<T = unknown> {
  /** Message type identifier (dot-separated namespace) */
  type: string
  /** Epoch milliseconds when the event occurred on the server */
  timestamp: number
  /** Protocol version (semver major.minor) for forward compatibility — server sends "1.0" */
  version: string
  /** Message payload — shape determined by `type` */
  payload: T
}
```

**Example** (real, as published by `ProcessingEventHandler`):

```json
{
  "type": "process.started",
  "timestamp": 1722182400000,
  "version": "1.0",
  "payload": {
    "taskId": "proc-1a2b3c4d",
    "galleryId": 1887292,
    "totalPages": 42,
    "processingType": "UPSCALE_2X",
    "processorId": "waifu2x"
  }
}
```

### 2.1 Download Topics Do NOT Use the Envelope **[IMPLEMENTED]**

The existing `DownloadProgress` DTO (`gid`, `state`, `downloaded`, `total`,
`speed`, `label`) is published **as a bare JSON object, without the envelope**,
on `/topic/download/{gid}` and `/topic/download/all`
(`DownloadProgressHandler.kt:12-21`).

The enveloped download types (`download.progress` / `download.state` /
`download.batch` on `/topic/download/progress` etc.) are **[PLANNED]** — no
publisher exists. Clients MUST parse download topics as the bare DTO.

### 2.2 Type Namespace Convention

Message types follow `{domain}.{event}` naming:

| Domain | Scope |
|--------|-------|
| `download` | Download task lifecycle (planned; see §3.1) |
| `process` | Image processing pipeline (implemented) |
| `image` | Individual image events (implemented: `image.enhanced.ready`) |
| `sync` | Device synchronization (planned) |
| `system` | Server health and errors (planned) |

### 3.2 Image Processing **[IMPLEMENTED]**

All four events are published by `ProcessingEventHandler` on **both**
`/topic/process/{taskId}` and `/topic/process/all`, wrapped in the §2 envelope
(`version: "1.0"`).

- **No server-side throttling**: one event is emitted per processed page;
  the "max 5 events/second" figure from earlier drafts is not enforced.
- `taskId` format: `proc-` + 8 hex chars (e.g. `proc-1a2b3c4d`,
  `ImageProcessingService.submitGallery`).
- Page numbers on the wire are **1-based** (the handler adds 1 to the
  service's internal 0-based index).

Emitted when an image enhancement job begins processing.

**Topic**: `/topic/process/{taskId}` or `/topic/process/all`

### 3.3 AI Enhancement (Reader Hot-Swap) **[IMPLEMENTED]**

#### `image.enhanced.ready`

**Critical message for I3 (AI enhancement hot-swap).**

Emitted by `ProcessingEventHandler` when a single page's enhanced version is
ready on disk. The reader component listens for this message and hot-swaps the
image `src` without interrupting the reading experience.

**Topic**: `/topic/gallery/{galleryId}/enhanced`

```typescript
interface ImageEnhancedReadyPayload {
  /** Gallery containing the enhanced page */
  galleryId: number
  /** Page number (1-based on the wire; the service tracks 0-based and the handler adds 1) */
  page: number
  /** URL to fetch the enhanced image (relative) */
  enhancedUrl: string
  /** URL of the original image (for reference/fallback) */
  originalUrl: string
  /** Processing type that was applied */
  processingType: 'UPSCALE_2X' | 'UPSCALE_4X' | 'DENOISE' | 'DENOISE_UPSCALE'
  /** Enhanced image width in pixels (0 when the format is not readable, e.g. webp) */
  width: number
  /** Enhanced image height in pixels (0 when the format is not readable, e.g. webp) */
  height: number
  /** File size in bytes (for cache management) */
  fileSize: number
}
```

Field provenance (`ImageProcessingService.executeTask`, `ProcessingEventHandler`):
`enhancedUrl` = `/api/v1/image/{galleryId}/{page}?enhanced=1`, `originalUrl` =
`/api/v1/image/{galleryId}/{page}`, `width`/`height` from the output file header
(0 when unreadable), `fileSize` from the output file (0 on read failure).

**Client behavior on receipt** (normative for I3 implementation):

1. Check if the page is currently displayed or in the preload cache.
2. Fetch the enhanced image from `payload.enhancedUrl` — equivalently construct
   `GET /api/v1/image/{galleryId}/{page}?enhanced=1` (0-based page; the optional
   `w=` resize query parameter is supported by the endpoint,
   `ImageProxyController.kt:87`).
3. On successful load, swap the displayed/cached image reference atomically.
4. Do NOT trigger a re-layout or scroll position change.
5. **If the enhanced image fails to load, silently keep the original.** The
   endpoint returns 404 when the enhanced file is not (yet) present — treat as
   "not ready", never as an error.
6. Update any local cache metadata to prefer the enhanced URL for future loads.

**Emission pattern**: The server emits one `image.enhanced.ready` per page as
each completes (not batched). This allows the reader to progressively upgrade
pages as the user reads, rather than waiting for the entire gallery.

## 5. Error Handling & Reconnection

### 5.1 STOMP Error Frames

The server's auth interceptor rejects a CONNECT with a STOMP ERROR frame
(`WsAuthChannelInterceptor.kt:37-43`):

```
message: Authentication required
content-type: application/json   (body is EMPTY — the error text lives in the message header)
```

**Client behavior on STOMP ERROR** (`useWebSocket.ts` `onStompError`):
1. Read `frame.headers['message']` (fallback `frame.body`).
2. If the error arrived before the first CONNECTED frame (i.e. the CONNECT was
   rejected — bad/missing token, protocol mismatch), give up immediately: stop
   the retry loop, set `connectionState = 'error'`, and surface the message via
   `authError` — retrying identical headers cannot succeed.
3. Errors after an established session set `connectionState = 'error'` and
   `lastError`; the library's backoff (§1.5) governs reconnection.

### 5.2 Connection Loss Detection

| Signal | Detection Method | Action |
|--------|-----------------|--------|
| Clean disconnect | STOMP DISCONNECT receipt | No reconnect needed |
| Network loss | Heart-beat timeout (30s) | Begin reconnection |
| Server crash | SockJS transport error | Begin reconnection |
| Tab hidden | `visibilitychange` event | Pause reconnect, resume on visible |

### 5.3 Missed Message Recovery

WebSocket is not guaranteed delivery. After reconnection:

1. Client calls `GET /api/v1/download/list` to get current download states.
2. Client calls `GET /api/v1/process/status/{taskId}` for each known processing
   task (there is no bulk "all tasks" endpoint; `POST /api/v1/process/gallery/{id}`
   starts a job, `POST /api/v1/process/cancel/{taskId}` cancels one).
3. Client re-subscribes to all active topics (automatic in the frontend manager).
4. For `image.enhanced.ready` events missed during disconnection, the reader
   SHOULD probe `GET /api/v1/image/{galleryId}/{page}?enhanced=1` when displaying
   a page — 404 means the enhanced file is not ready yet; keep the original.

### 5.4 Server-Side Error Propagation

- Processing failures are covered by the implemented `process.failed` event
  (§3.2), including cancellation.
- The `system.error` topic and enveloped `download.state` (`state: 'failed'`)
  propagation from earlier drafts are **[PLANNED]** — not emitted today.
- Download failures are only observable via the bare `DownloadProgress` DTO's
  numeric `state` field and REST (`GET /api/v1/download/list`, `DownloadItem.error`).

| Screen | Topics to Subscribe |
|--------|-------------------|

### 6.4 Gallery-Specific Filtering

- `/topic/download/{gid}` receives ONLY that gallery's bare `DownloadProgress`
  DTO. `/topic/download/all` receives every gallery's DTO. The server publishes
  each event to both topics (`DownloadProgressHandler`).
- `/topic/gallery/{galleryId}/enhanced` receives ONLY `image.enhanced.ready`
  for that gallery.

The rate figures below are **aspirational** — the current implementation applies
no server-side throttling:

| Message Type | Max Rate (aspirational) | Reality |
|-------------|----------|----------|
| `download.progress` (bare DTO) | 2/sec per task | No throttle in `DownloadProgressHandler`; forwards every event |
| `process.progress` | 5/sec per task | No throttle; one event per processed page |
| `system.health` | 1/30sec | Topic not implemented |
| `image.enhanced.ready` | No throttle | One per page completion (naturally bounded by GPU) |

## 7. Versioning Strategy

### 7.1 Protocol Version

The protocol follows **semantic versioning** (MAJOR.MINOR.PATCH):

- **MAJOR**: Breaking changes (message removal, envelope restructure).
  Requires coordinated client + server upgrade.
- **MINOR**: Additive changes (new message types, new optional payload fields).
  Backward compatible; old clients ignore unknown types.
- **PATCH**: Documentation fixes, no wire changes.

Current version: **1.0.0**

### 7.2 Version Negotiation

1. The `version` field in every envelope carries the protocol version (server
   sends `"1.0"`).
2. Clients SHOULD ignore messages with a MAJOR version higher than supported.
3. Clients SHOULD handle unknown `type` values gracefully (log + discard).
4. New optional fields in payloads MUST NOT break clients that don't read them.

### 7.3 Deprecation Policy

- Deprecated message types/topics are announced one MINOR version ahead.
- The `version` field in deprecated messages remains unchanged.
- Server logs a warning when a client subscribes to a deprecated topic.
- Deprecated topics are removed in the next MAJOR version.

### 7.4 Download Topic Status

**Reality**: the only download topics the server publishes are the two bare-DTO
topics — `/topic/download/{gid}` and `/topic/download/all`. Both carry the raw
`DownloadProgress` DTO (`gid`, `state`, `downloaded`, `total`, `speed`, `label`).

The enveloped download topics (`/topic/download/progress`,
`/topic/download/state`, `/topic/download/batch`) are **[PLANNED]**; the earlier
"server SHALL publish both legacy and new formats during migration" clause does
not apply because the enveloped variants do not exist yet.

| Planned (v2.0 target) | Current |
|--------|-------------|
| `/topic/download/{galleryId}` (envelope) | `/topic/download/{gid}` (bare DTO) — implemented |
| `/topic/download/progress` (envelope) | `/topic/download/all` (bare DTO) — implemented |
| `galleryId` field | `gid` field |
| `state` as string enum | `state` as integer |
| `downloadedPages` | `downloaded` |
| `totalPages` | `total` |

Frontend migration target: Wave 3 I2 (WS integration task).


(`WebSocketConfig.kt:28-32` splits on commas and passes the list to

### C.2 Message Publishing Pattern

**Download topics publish the BARE DTO** (no envelope) — `DownloadProgressHandler.kt`:

```kotlin
messagingTemplate.convertAndSend("/topic/download/${progress.gid}", progress)
messagingTemplate.convertAndSend("/topic/download/all", progress)
```

**Processing/enhanced topics publish the envelope** — `ProcessingEventHandler.kt`:

```kotlin
private fun publish(topic: String, type: String, payload: Map<String, Any?>) {
    val envelope = mapOf(
        "type" to type,
        "timestamp" to System.currentTimeMillis(),
        "version" to "1.0",
        "payload" to payload
    )
    messagingTemplate.convertAndSend(topic, envelope)
}
```

### C.3 Enhanced Image Emission (I3 Integration)

Implemented in `ImageProcessingService.executeTask` +
`ProcessingEventHandler.handleProcessingEvent`. On page completion the service
emits `ProcessingEvent.EnhancedReady` with:

```kotlin
ProcessingEvent.EnhancedReady(
    taskId = taskId,
    galleryId = galleryId,
    page = page,                                   // 0-based internally
    enhancedUrl = "/api/v1/image/$galleryId/$page?enhanced=1",
    originalUrl = "/api/v1/image/$galleryId/$page",
    processingType = options.type,
    fileSize = Files.size(outputPath),             // 0 on failure
    width = readImageWidth(outputPath),            // 0 when unreadable (e.g. webp)
    height = readImageHeight(outputPath),
)
```

The handler adds 1 to `page` before publishing (1-based on the wire) and emits
on `/topic/gallery/$galleryId/enhanced`.

## Appendix D: Client Integration Example (Vue 3)

```typescript
// web-frontend/src/composables/useEnhancedImage.ts (I3 task)
// Matches the production configuration in useWebSocket.ts (§1.5).
import { Client, ReconnectionTimeMode } from '@stomp/stompjs'
import SockJS from 'sockjs-client/dist/sockjs'
import type { WsEnvelope, ImageEnhancedReadyPayload } from '@/types/websocket'

export function useEnhancedImage(galleryId: number, token: string) {
  let client: Client | null = null
  const enhancedUrls = new Map<number, string>() // page → enhancedUrl

  function connect(onReady: (page: number, enhancedUrl: string) => void) {
    client = new Client({
      webSocketFactory: () => new SockJS('/ws'),
      connectHeaders: { login: token, Authorization: `Bearer ${token}`, passcode: '' },
      reconnectDelay: 1000,
      maxReconnectDelay: 30000,
      reconnectTimeMode: ReconnectionTimeMode.EXPONENTIAL,
      heartbeatIncoming: 10000,
      heartbeatOutgoing: 10000,
      onConnect: () => {
        client?.subscribe(
          `/topic/gallery/${galleryId}/enhanced`,
          (message) => {
            const envelope = JSON.parse(message.body) as WsEnvelope<ImageEnhancedReadyPayload>
            if (envelope.type === 'image.enhanced.ready') {
              const { page, enhancedUrl } = envelope.payload
              enhancedUrls.set(page, enhancedUrl)
              onReady(page, enhancedUrl)
            }
          }
        )
      },
    })
    client.activate()
  }

  function disconnect() {
    client?.deactivate()
  }

  // Fetch the enhanced image; 404 → keep the original silently.
  async function loadEnhanced(page: number): Promise<string | null> {
    const url = `/api/v1/image/${galleryId}/${page}?enhanced=1`
    const res = await fetch(url)
    return res.ok ? url : null
  }

  return { connect, disconnect, getEnhancedUrl: (p: number) => enhancedUrls.get(p), loadEnhanced }
}
```
